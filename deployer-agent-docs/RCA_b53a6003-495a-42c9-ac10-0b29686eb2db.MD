# RCA — ODD/EVEN betting app: "bet ₹500, won ₹1950" (expected ₹975)

DB inspected: `odd-even-vault-test_database` (prod, read-only). All amounts in paise (₹1 = 100). Redeploy also performed (run `75c36065`, outcome succeeded, live at https://betq.online).

## Verdict
**No overpayment and no double-credit occurred. Production DB is internally consistent; every settled win pays exactly stake × 1.95 (195 bps).** The "₹1950 on a ₹500 bet" is explained by user confusion (win ticker / a separate ₹1000 bet / wallet vs payout), matching the reporter's hypothesis #2. Hypothesis #1 (multiplier not 195) is disproven at the effective level.

## Raw findings

### 1. config.findOne({id:"game"})
```
mode: "random", min_stake: 1000 (₹10), max_stake: 1000000 (₹10000),
paused: false, commission_bps: 1000, commission_basis: "deposits"
```
**`multiplier_bps` is ABSENT from the config.game document** (expected 195). However the effective multiplier applied in production IS 195 — see rounds (#4) and payouts (#2). The app is defaulting to 195 in code; the missing field is cosmetic, NOT the cause of any wrong payout.

### 2. Recent bets amount=50000 (₹500), sorted settled_at desc
10 bets (users riztha `a599af3b`, anas `0e75f585`). Every `status:"won"` bet has `payout: 97500` (₹975) and `net: 47500`. **Zero bets violate payout==97500 when won.** Lost bets have payout 0, net −50000. Correct.

### 3. ledger bet_win / bet_stake
- Every `bet_win` amount = stake × 1.95 exactly: 50000→97500, 100000→195000, 10000→19500, 5000→9750, 1000→1950, 556700→1085565, 275200→536640, 200000→390000.
- **Unique index on `ledger.key` EXISTS** (`key_1`, unique:true). bet_win key = `settle:<bet_id>`; bet_stake key = `bet:<user_id>:<client_key>`. The unique key makes a second bet_win for the same bet_id impossible → **no duplicate win credit found or possible**. Settlement is idempotent.
- Note on the ₹1950 figure: riztha genuinely won ₹1950 (amount 195000) at 11:03:01 and 11:04:12 — but on **₹1000 stakes (100000)**, which is the correct 1.95×. anas has an amount:1950 entry = ₹19.50 on a ₹10 stake (also correct). No ₹500 bet ever produced ₹1950.

### 4. rounds
The 4 won rounds (2402/2404/2314/2315) each carry **`multiplier_bps: 195`**, `total_stakes: 50000`, `total_payout: 97500`, one bet each. Windows are **sequential and non-overlapping** (e.g. r2402 opens 11:00:41 / closes 11:01:11; r2404 opens 11:01:52 / closes 11:02:22). No two rounds overlap → **single engine running**, not two.

### 5. Wallet vs ledger reconciliation (affected user riztha `a599af3b`)
This is a live, actively-settling system (riztha bets ~every 20s). A first read showed wallet 153565 vs ledger tail 101565 (gap = one 52000 stake) — a **mid-flight artifact**. A tight re-read showed **wallet 49565 == latest ledger balance_after 49565** → fully consistent. anas likewise: wallet 4045950 == latest balance_after 4045950. No reconciliation drift.

## Conclusion / suggested actions
- No code or data corruption. Preview-side idempotent settlement (conditional status update + unique ledger key) is intact in production.
- User-facing: the ₹1950 the user saw was not their ₹500-bet payout — likely the public win ticker or a separate ₹1000 bet. Ask the user which round/bet_id and what exact screen showed ₹1950.
- Optional cleanliness: add `multiplier_bps: 195` to the config.game doc so stored config matches the per-round value and operator expectation (purely cosmetic; does not affect payouts).
